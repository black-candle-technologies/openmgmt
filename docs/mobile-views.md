# Account-scoped server read views

The sync server exposes read-only task/project presentation endpoints for the Black Candle mobile BFF. Android receives fixed presentation DTOs through the BFF; it does not replay `omgp/1`, build a task database, filter, sort, or calculate task metrics.

## Routes

All require `Authorization: Bearer <account access credential>`, a configured `OPENMGMT_AUTH_ISSUER`, verified email, and the existing explicit `openmgmt:tasks:read` product scope. That scope includes project context used by tasks; no new scope registry is invented here. Legacy `identity` alone is denied by these routes even though existing sync/MCP behavior may permit it. Original bearer forwarding from the BFF retains the actual account and product scope. The BFF independently requires an allowlisted first-party mobile OAuth credential and service entitlement. Do not give Android an OpenMGMT device token or upstream service/admin credential.

| Method | Route | Response |
| --- | --- | --- |
| GET | `/api/views/v1/overview` | `schema_version`, `service_id:openmgmt`, `screen`, `availability`, recent task/project `sections`, read-only `capabilities`, `revision` |
| GET | `/api/views/v1/items?kind=task&q=...&filter_id=active&sort_id=updated_desc&limit=25&cursor=...` | Standard server `ListPageView` with rows, advertised filters/sorts, selected choices, empty state and opaque next cursor |
| GET | `/api/views/v1/items/task/{id}` | Standard `DetailView`: screen, description/status/updated display fields, revision, empty actions |
| GET | `/api/views/v1/items/project/{id}` | Same detail shape for account-owned projects |

`kind` is `task` (default) or `project`. `filter_id` is `active` (default, meaning not archived), `archived`, or `all`; completed tasks are still non-archived until an explicit archive event. `sort_id` is `updated_desc` (default) or `title_asc`, each with stable ID tie breaking. `limit` is 1–50. Search is trimmed, Unicode-lowercased on the server, and matched against materialized title/description search text. Search is literal, not SQL wildcard syntax. Query size is bounded to 200 UTF-8 bytes; unsupported/extra query fields and malformed cursors are rejected.

List row IDs are `task_{source_id}` or `project_{source_id}`; detail routes returned to Android are `services/openmgmt/items/{row_id}`. The BFF decodes the fixed prefix to the appropriate upstream detail route. The BFF may provide a `projects` presentation filter mapping to `kind=project`, allowing generic mobile navigation to browse both kinds without trusting remote URLs.

Responses are `Cache-Control: private, no-store` and vary by Authorization. Missing/invalid bearer is 401; missing product scope or unverified email is 403; another user's or unknown item is 404; invalid query/cursor is 400; a cursor invalidated by accepted data changes is 409; disabled account auth or issuer/database outage is 503. No secret, bearer or raw event payload appears in presentation responses. No mutation endpoint is introduced.

## Projection and ownership semantics

The additive `mobile_projection` SQLite table has primary key `(account_id,kind,id)`. A startup migration backfills existing events only through devices with an established `server_devices.account_id`. A server-owned random HMAC cursor key is persisted in `server_state`; protect that database like the existing device-token database and never publish the key. Keep a database backup before deployment. The source event log and existing sync routes remain in place.

Each newly accepted sync event updates its projection in the **same SQLite transaction** as event ingestion. Duplicate events are not projected twice. Account ownership is obtained from the authenticated source device's persisted account binding, never from an event's actor/target/workspace or a query parameter. Two accounts may use the same task/project ID without sharing rows. Open-registration global/unbound events never become publicly readable through these routes. A legacy device claim requires actual current device-token proof; a tokenless old device needs explicit administrative migration or a new device. Account claim is now persisted (the prior registration SQL omitted this despite returning a bound account), and claimed historical events are backfilled in that transaction.

Reduction follows existing core sync semantics: each accepted full `created`, `updated` or task `transitioned` snapshot replaces the current entity in server ingestion order. It is **not a new CRDT/conflict-resolution policy**, and client `updated_at` is used for display/sort rather than authority to choose a winner. Archive events mark the task canceled/project archived and preserve its display fields. An archive arriving before its full entity remains undisplayable rather than producing a fabricated row. Later accepted full snapshots follow the existing overwrite behavior. Future collaboration/member/workspace visibility is not inferred; these endpoints expose only the owning account's synced device data.

Snapshots are decoded through current typed core `Task`/`Project` models. Wrong payload IDs, invalid models, unsupported operations, oversized snapshots, invalid IDs or excessive title/description bounds mark that entity undisplayable; its old row is not falsely presented as current. Overview reports partial availability when such rows exist. Organization events remain in sync storage but are not exposed as a mobile feature. Entities with valid IDs/title/description but unsupported future fields follow serde-compatible decoding; unsupported future enum values produce partial availability. This is an honest projection of server-received data, not a claim that every desktop entity has synced successfully.

HMAC-SHA256 cursors bind the account, normalized query, kind, filter, sort, page size and projection revision. They carry only nonsecret query/position data. A changed dataset requires restarting the list, preventing stale pagination from silently skipping/repeating changed records. SQL parameters carry all client inputs; only allowlisted sort SQL is selected internally.

## Validation and deployment limits

`cargo test -p openmgmt-server` passes **23 tests**: the original 16 and seven new projection/route tests for account separation, product scopes, verified identities, denied open/global reads, identical cross-account entity IDs, Unicode search, page/cursor tampering and binding, stable pages, update/archive/detail behavior, legacy claim proof, existing-event backfill, malformed snapshot suppression, query limits, and disabled auth. Run `cargo fmt -p openmgmt-server -- --check` and these tests before publishing.

Local tests ran on Windows with Rust/Cargo 1.97.1 (stable MSVC toolchain), using temporary/in-memory SQLite and a loopback mock OAuth issuer. They do **not** demonstrate production deployment, authentic user data, multi-node behavior or mobile/device interoperability. The actual public OAuth issuer, BFF base URL configuration and first-party OAuth product-scope grants must be configured and verified. Existing `AccountAuth` has a five-minute successful-token validation cache; read revocation can therefore lag by that bounded cache interval. This work does not change shared protocol caching or claim immediate revocation for upstream read views.

The SQLite connection is serialized as in the current server. Initial backfill may prolong startup for a large retained event log, and claiming a legacy account can replay that account's log. Test deployment with realistic data volume; no database-wide cardinality/performance benchmark was run. Existing sync transport admission limits, quotas, request/rate limiting and multi-node authorization/cache review remain operational/security review work; this read API is not an exhaustive repository audit. The new routes perform no administrative operations and expose no unrestricted upstream proxy.

Deploy OpenMGMT first, confirm an account with explicitly granted product read scope can see only its own genuine synced rows, then enable its fixed BFF adapter. Verify a second account gets 404 for the first user's detail IDs; identity-only, unverified, expired/revoked and missing credentials cannot obtain data. Confirm pushes update the overview/list/detail, and deliberately archived tasks/projects move to the advertised archived filter. Keep unsupported mutations hidden.
